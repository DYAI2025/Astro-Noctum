## Context
The project uses `3-code/tasks.md` as the single source of truth for all development tasks, organized into sprints with clusters. Bug reports use BUG-NN IDs. Tasks use TASK-kebab-name IDs.

## Your Task

Process an intake document (file path or inline text) containing change requests, bug reports, and feature requests. Evaluate each item against the existing task list, deduplicate, and integrate new items into the correct sprints.

### Steps

1. **Read the intake document** — parse all items with their descriptions, acceptance criteria, and priority
2. **Read `3-code/tasks.md`** — understand current sprints, clusters, and task statuses
3. **For each intake item, classify:**
   - **REDUNDANT** — already tracked by an existing task (list the matching TASK-ID)
   - **EXTENDS** — overlaps with existing task, needs Notes update (list TASK-ID + what to add)
   - **NEW BUG** — functional regression or data issue → assign BUG-NN ID
   - **NEW FEATURE/UX** — new capability or layout change → assign TASK-kebab-name
   - **NEEDS REFINEMENT** — product question must be answered before implementation → flag for `/po-refinement`
4. **Present evaluation table** — show all items with classification before making changes
5. **Wait for user confirmation**
6. **Write changes to tasks.md:**
   - Add new bugs to Bug Tracker section with next BUG-NN
   - Add new tasks to existing sprint clusters or create new sprint if needed
   - Update Notes on extended tasks
   - Mark refinement items with "NEEDS REFINEMENT:" prefix in Notes
7. **Report summary** — counts per classification, new sprint if created, refinement items collected

### Guardrails
- Never duplicate — always grep tasks.md first
- Never create a new sprint when items fit an existing one
- Always flag items needing product decision separately
- Preserve task ID uniqueness
- Use P1 for bugs blocking production, P2 for UX/content bugs, P3 for polish
